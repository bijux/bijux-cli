# Completions And Command Surface

The installed command surface comes from `bijux-dag-app`. The CLI package adds
one process-owned command: shell completion generation.

## Command Authority

The stable visible routes, lane discovery, global flags, help text, and
command-specific arguments are defined in the app command model. The wrapper
does not maintain a second list.

The public operator boundary is the default visible `bijux-dag --help`
surface. Experimental, simulated, and internal inventory remains governed by
app lane policy and explicit opt-in.

## Completion Command

Completion invocation uses:

```text
bijux-dag completions --shell <shell>
```

Supported values are:

- `bash`;
- `zsh`;
- `fish`;
- `elvish`;
- `powershell`.

`clap_complete` receives the complete app-owned command plus the completion
command and emits a script for the installed binary name `bijux-dag`.

## Compatibility Rules

- Generated completion routes must match the current command tree.
- Unsupported shell values fail as usage, not an empty script.
- Completion generation performs no DAG IO or runtime initialization.
- Scripts go to stdout without explanatory text.
- Adding a supported shell requires command validation and a completion test.
- Removing or renaming a command requires reference and completion review.

## Reference Relationship

Checked-in command reference is generated by `bijux-dag-app`, not this crate.
Completion and reference are two projections of the same command model.
Drift in either is a contract failure.

## Verification

Package contract tests cover completion availability and command delegation.
App command-tree snapshots, generated-reference contracts, surface policy
tests, and operator schema lockstep tests prove the shared authority.

Manual inspection may use:

```bash
cargo run --locked -p bijux-dag-cli -- completions --shell bash
```

The output is generated data and should be directed to `artifacts/` when
retained during repository work.
