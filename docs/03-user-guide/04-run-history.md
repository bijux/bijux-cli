# Run History

Run history is where you decide whether behavior changed, when it changed, and whether the change is definition, runtime, or environment-driven.

## Reading history as evidence

Do not treat history as a timestamp list. Treat it as a comparison index:

- find the newest failing run,
- find the last known-good baseline,
- compare the pair with inspect/replay/diff,
- classify whether the issue is recurring or newly introduced.

## Ancestry in one place

History includes different provenance classes:

- original run: native local execution,
- replayed run: generated by replay workflow,
- imported run: reconstructed from external bundle evidence.

These are all valid, but they are not equally trustworthy in every decision context. Imported runs carry external trust boundaries; replayed runs carry baseline dependency.

## Regression workflow example

```bash
bijux-dag run history --limit 30
bijux-dag inspect run --run-id RUN_20260309_211
bijux-dag inspect run --run-id RUN_20260309_204
bijux-dag replay --run-id RUN_20260309_211
bijux-dag diff run --left RUN_20260309_204 --right RUN_20260309_211
```

Interpretation rule:

- same failure node across many runs usually indicates deterministic defect,
- drift only after environment/tool change usually indicates bounded non-equivalence.

## What history can and cannot reconstruct

History can reconstruct:

- run status progression,
- node-level failure recurrence,
- artifact lineage references that were retained.

History cannot reconstruct:

- missing payloads removed by retention policy,
- external side effects never captured as artifacts,
- equivalent-context proof without replay/diff evidence.
